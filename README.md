# Hourly PM2.5 Forecasting for Beijing with a Deep Neural Network

An end-to-end machine learning project that predicts hourly PM2.5 air pollution in Beijing from five years of meteorological and pollution history. The pipeline covers data cleaning, exploratory analysis, time-series feature engineering, a leakage-aware temporal split, a reproducible preprocessing pipeline, a regularised feed-forward neural network (TensorFlow/Keras), and residual diagnostics.

## 1. Problem Statement

PM2.5 (particulate matter under 2.5 µm) is one of the most health-relevant air pollutants. Accurate short-term estimates support public health alerts and planning.

**Task:** regression. Given the recent PM2.5 history and the current-hour weather readings, predict the PM2.5 concentration (µg/m³) for the hour being forecast.

All history-based features are built only from *past* observations (lags and rolling statistics are shifted by one step), so the target hour's own PM2.5 is never used as an input.

## 2. Results at a Glance

| Metric (test set = all of 2014, 8,760 hourly samples) | Neural network | Persistence baseline* |
|---|---|---|
| MAE (µg/m³) | 13.33 | 11.82 |
| RMSE (µg/m³) | 23.39 | 21.91 |
| R² | 0.9379 | 0.9455 |

\*Persistence baseline = "predict that PM2.5 this hour equals last hour" (`pm25_lag1`), evaluated on the identical test split. See [Section 8](#8-limitations-and-honest-assessment) for what this means and how I plan to improve on it.

**Key takeaways**

- The network explains ~94% of the variance in unseen data from a full held-out year.
- PM2.5 is extremely persistent (lag-1 autocorrelation = 0.966), which is why a naive persistence baseline is a very strong competitor at a 1-hour horizon.
- The model has not yet beaten that baseline. Section 8 lists the concrete steps to change that.

## 3. Dataset

- **Source:** UCI Machine Learning Repository, *Beijing PM2.5 Data* (US Embassy in Beijing readings combined with meteorological data).
- **Coverage:** hourly records, 1 Jan 2010 to 31 Dec 2014 (43,824 rows, 12 columns after dropping the index).
- **Missing data:** 2,067 missing PM2.5 values (about 4.7%).

| Column | Description |
|---|---|
| `year`, `month`, `day`, `hour` | Timestamp components |
| `pm2.5` | **Target.** PM2.5 concentration (µg/m³) |
| `DEWP` | Dew point (°C) |
| `TEMP` | Temperature (°C) |
| `PRES` | Pressure (hPa) |
| `cbwd` | Combined wind direction (`NE`, `NW`, `SE`, `cv` = calm/variable) |
| `Iws` | Cumulated wind speed (m/s) |
| `Is` | Cumulated hours of snow |
| `Ir` | Cumulated hours of rain |

## 5. Methodology

### 5.1 Data loading and cleaning
- Dropped the redundant row-index column (`No`).
- Sorted chronologically by `year, month, day, hour` and reset the index, so every rolling/lag operation is temporally correct.
- Sanity-checked the value ranges of all time components.
- **Missing PM2.5** values were filled with **linear interpolation**, which is appropriate for a smooth, highly autocorrelated hourly signal.

### 5.2 Exploratory data analysis
| Analysis | Finding |
|---|---|
| **Target distribution** | Strongly right-skewed (skewness about 1.8, mean about 99 µg/m³, max 994). A `log(1 + x)` transform gives a far more symmetric distribution, motivating a **log-transformed target**. |
| **Correlation heatmap** | Raw meteorological features are only weakly correlated with PM2.5 (the strongest is `Iws` with |r| ≈ 0.25), suggesting the signal is mostly in the temporal dynamics of PM2.5 itself. |
| **Seasonality** | Highest average PM2.5 in Feb (about 126), Oct (about 120) and Jan (about 113); lowest in May and Aug (about 81). |
| **Diurnal pattern** | Peaks around 01:00 (about 113 µg/m³) and is lowest in the mid-afternoon (about 86 µg/m³ at 15:00). |
| **Year over year** | Annual means are broadly stable (about 91 to 104 µg/m³), with no dramatic trend across 2010–2014. |
| **Wind direction** | Clear separation: north-westerly winds are associated with the cleanest air (median about 32), while calm/variable (`cv`) and south-easterly winds carry the highest pollution (median about 91 to 98). |
| **Meteorology scatter plots** | Examined `TEMP`, `DEWP`, `PRES` and `Iws` against PM2.5 to check for non-linear relationships. |
| **Autocorrelation (lags 1 to 48)** | Lag-1 = **0.966**, lag-2 = 0.920, lag-24 = 0.402. Very strong short-term memory plus a daily cycle, which drove the choice of lag windows below. |

### 5.3 Feature engineering
All temporal features use `shift(1)` before any rolling or exponential operation, which prevents target leakage.

- **Cyclical encoding** of `hour` and `month` via sine/cosine, so 23:00 and 00:00 (or Dec and Jan) are neighbours in feature space. The raw `hour` and `month` columns were then dropped.
- **Lag features:** PM2.5 at t-1, t-2, t-3, t-6, t-12, t-24.
- **Rolling means** over 3, 6, 12 and 24 hours.
- **Rolling standard deviations** over 3, 6, 12 and 24 hours (volatility signal).
- **Exponentially weighted means** with spans 3, 6, 12 and 24 (recency-weighted trend).
- Dropped the first 24 rows that lack a full history window: 43,824 → **43,800** rows, **32 columns**.

### 5.4 Train/test split
- **Chronological 80/20 split with no shuffling**, since random splitting would leak future information into training.
- **Train:** 35,040 rows (2010–2013). **Test:** 8,760 rows (2014, a fully unseen year).
- **Target transform:** `log1p(PM2.5)` for training. Predictions are converted back with `expm1` and clipped at 0, and all reported metrics are computed in the original µg/m³ scale.

### 5.5 Preprocessing pipeline
Built with `scikit-learn`'s `ColumnTransformer`, fitted **on the training data only**:

| Feature type | Columns | Transformation |
|---|---|---|
| Numerical (30) | Weather, cyclical time, lags, rolling and EMA features | `RobustScaler` (median/IQR scaling, resistant to PM2.5 spikes) |
| Categorical (1) | `cbwd` | `OneHotEncoder(handle_unknown='ignore')` |

Output: **34 model inputs**. The fitted transformer is serialised to `preprocessor.pkl` so inference uses the exact same transformations.

## 6. Model Architecture and Training

A fully connected network regularised with batch normalisation and dropout:

```
Input (34)
 → Dense(256, ReLU) → BatchNorm → Dropout(0.2)
 → Dense(128, ReLU) → BatchNorm → Dropout(0.2)
 → Dense(64,  ReLU) → BatchNorm → Dropout(0.2)
 → Dense(32,  ReLU) → BatchNorm → Dropout(0.1)
 → Dense(1, linear)
```

**Parameters:** 54,145 total (53,185 trainable).

| Setting | Value |
|---|---|
| Optimiser | Adam, initial learning rate 1e-3 |
| Loss | **Huber** (robust to outliers and pollution spikes) on the log-scale target |
| Metric | MAE (log scale) |
| Batch size / max epochs | 128 / 200 |
| `EarlyStopping` | monitor `val_loss`, patience 15, restore best weights |
| `ReduceLROnPlateau` | factor 0.5, patience 5, min LR 1e-6 |
| Reproducibility | NumPy and TensorFlow seeds fixed to 42 |

**Training outcome:** the learning rate was halved several times as the loss plateaued, early stopping triggered at epoch 56, and the weights from the best epoch (41) were restored.

## 7. Evaluation

**Test-set metrics (original µg/m³ scale):**

| Metric | Value |
|---|---|
| MAE | 13.33 µg/m³ |
| RMSE | 23.39 µg/m³ |
| R² | 0.9379 |

**Diagnostics included in the notebook:**
- Loss and MAE learning curves (train vs validation).
- Actual vs predicted scatter plot against the perfect-prediction line.
- Residuals vs predicted values (checks for heteroscedasticity).
- Residual histogram and a **Q-Q plot** (checks normality of errors).
- Residual summary: mean = +5.32 µg/m³, standard deviation = 22.77 µg/m³. A positive mean residual means the model **under-predicts slightly on average**, which is a common side effect of back-transforming from log space (`expm1` of a log-space prediction tends toward the median rather than the mean).

## 8. Limitations and Honest Assessment

Being explicit about weaknesses is part of good ML practice. These are the issues I identified in the current version:

1. **Does not yet beat the persistence baseline.** Predicting "same as last hour" gives MAE 11.82 / RMSE 21.91 / R² 0.945 on the same test set, slightly better than the network. This is unsurprising given the 0.966 lag-1 autocorrelation, but it means the model's added value is unproven at this horizon.
2. **Validation set = test set.** Early stopping and learning-rate scheduling monitor the test data, so the reported metrics are mildly optimistic. A proper setup uses a separate validation window (for example 2013) and touches the 2014 test set only once.
3. **`year` is used as an input feature.** The test year (2014) never appears in training, so its scaled value lies outside the training range. `year` (and arguably `day`-of-month) adds little real signal and should be removed.
4. **Interpolation before splitting.** Linear interpolation of missing PM2.5 values uses neighbouring points on both sides, so it can leak a small amount of future information across the split boundary. A causal fill (forward-fill) or split-then-impute approach is safer.
5. **Small, single-station dataset.** One monitoring site over five years and a single train/test split limit how far the results generalise.
6. **Slight bias** (positive mean residual) from the log back-transformation.

## 9. Future Work

- Add persistence and seasonal-naive baselines *inside* the notebook and report relative improvement.
- Fix the leakage-related issues above (proper validation split, remove `year`, causal imputation).
- **Walk-forward (rolling-origin) cross-validation** for more reliable error estimates.
- Compare against gradient-boosted trees (LightGBM/XGBoost), which are strong on tabular lag features.
- Try sequence models (LSTM/GRU/1D-CNN/Temporal Fusion Transformer) on raw windows.
- Move to **multi-step forecasting** (t+6, t+24 hours), where weather features should add real value beyond persistence.
- Prediction intervals via quantile loss, plus bias correction after back-transformation.
- Hyperparameter search (Optuna), SHAP feature importance, and experiment tracking (MLflow / Weights & Biases).
- Serve the model behind a small REST API (FastAPI) with a Docker image.

## 11. Using the Saved Model

```python
import joblib
import numpy as np
from tensorflow.keras.models import load_model

model = load_model("pm25_ann_model.keras")
preprocessor = joblib.load("preprocessor.pkl")

# X_new: a pandas DataFrame with the same feature columns used in training
# (weather variables, cyclical hour/month, PM2.5 lags, rolling and EMA features, cbwd).
X_proc = preprocessor.transform(X_new)
pred_log = model.predict(X_proc).flatten()
pm25_pred = np.maximum(np.expm1(pred_log), 0)   # back to µg/m³
```

> The lag, rolling and EMA features require at least the previous 24 hours of PM2.5 readings, so they must be computed with the same logic as in Section 5.3 before calling the preprocessor.
